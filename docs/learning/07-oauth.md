# 학습 07. 소셜 로그인(OAuth)과 구글 로그인

> 순서: ① 무엇인가 → ② 없으면 무슨 문제 → ③ 우리 프로젝트의 어디에 있나 → 확인 질문(객관식)

---

## 1. OAuth란?

**"내 비밀번호를 알려 주지 않고, 다른 서비스(구글)가 '이 사람 맞아요'라고 대신 보증해 주는 방식."**

비유: 호텔 체크인
- 호텔(노트립)은 내 신분을 직접 검사하지 않는다.
- 대신 **여권을 발급한 나라(구글)**가 "이 사람 맞다"고 보증하면 믿는다.
- 호텔은 내 여권 비밀번호 같은 건 **절대 모른다.**

**② 없으면?**
- 사용자는 서비스마다 비밀번호를 새로 만들어야 한다. (귀찮고, 같은 비밀번호를 돌려 쓰게 됨)
- 우리는 비밀번호를 안전하게 보관할 책임을 진다.
- OAuth를 쓰면 우리 앱은 **구글 비밀번호를 한 번도 보지 않는다.** 비밀번호 입력은 구글 사이트에서만 일어난다.

## 2. 구글 로그인의 흐름

```
① 노트립에서 "Google로 계속하기" 클릭
     │  supabase.auth.signInWithOAuth({ provider: 'google' })
     ▼
② 구글 로그인 화면 (accounts.google.com) ← 비밀번호는 여기서만 입력
     │  "노트립이 이메일, 이름을 보려고 해요. 허용할까요?" (동의 화면)
     ▼
③ Supabase 서버 (https://<프로젝트>.supabase.co/auth/v1/callback)
     │  구글에게 "이 사람 정보 주세요" 확인 → Supabase에 사용자 생성/로그인
     ▼
④ 노트립으로 돌아옴 (redirectTo 주소, 로그인 정보가 주소에 붙어 있음)
     │  supabase-js가 주소에서 읽어 세션 저장
     ▼
⑤ AuthProvider가 onAuthStateChange로 알림 받음 → 로그인 완료
```

**중요한 점**
- 앱이 **페이지를 떠났다가 돌아온다.** 그래서 `signInWithGoogle()`은 결과를 돌려주지 않는다. 결과는 ④⑤에서 받는다.
- 로그인이 끝나면 결과는 **이메일 로그인과 똑같은 세션**이다. → 학습 노트 06의 상태 관리 코드를 그대로 쓴다. 고친 곳이 없다.
- **소셜 로그인은 가입과 로그인이 따로 없다.** 처음이면 자동으로 가입된다.

## 3. 등록해야 하는 것들

구글 입장에서는 "노트립이 누군데 내 사용자 정보를 달래?"가 된다. 그래서 **구글에 앱을 미리 등록**해야 한다.

| 어디에 | 무엇을 | 왜 |
|---|---|---|
| **Google Cloud** | OAuth 클라이언트 만들기 → **Client ID**, **Client Secret** 받기 | 구글이 "노트립"을 알아보는 신분증 |
| **Google Cloud** | 승인된 리디렉션 URI에 `https://<프로젝트>.supabase.co/auth/v1/callback` 등록 | 로그인 후 **이 주소로만** 결과를 보내라는 허용 목록. 아무 주소로나 보내면 해커 사이트로 빼돌릴 수 있다 |
| **Supabase** | Google 공급자 켜고 Client ID, **Secret** 입력 | ③에서 Supabase가 구글과 대화할 때 쓴다 |
| **Supabase** | Redirect URLs에 `.../**` 등록 | ④에서 돌아올 수 있는 우리 앱 주소 허용 목록 |

**Client Secret은 Supabase에만 넣는다.** 우리 코드나 `.env.local`, Vercel에는 넣지 않는다. 브라우저 코드는 공개되기 때문이다. (학습 노트 04: `VITE_` 변수는 공개된다)

**허용 목록이 두 번 나오는 이유**: 리디렉션은 두 번 일어난다(② → ③, ③ → ④). 각 단계마다 "이 주소로 보내도 되나?"를 검사한다.

## 4. 우리 프로젝트에서

| 파일 | 변경 |
|---|---|
| `features/auth/api.ts` | `signInWithGoogle(redirectPath)` 추가 |
| `features/auth/pages/LoginPage.tsx` | "Google로 계속하기" 버튼 (임시 디자인) |

- `redirectTo: window.location.origin + redirectPath`: RequireAuth가 기억해 둔 **원래 가려던 주소**로 돌아온다. 그래서 Supabase Redirect URLs를 `/**`(그 아래 모든 경로)로 등록한다.
- 구글로 떠나는 동안 버튼을 **다시 켜지 않는다.** 이동 중에 또 눌리는 것을 막기 위해서다.
- 정식 디자인에서는 **구글 버튼 디자인 가이드**(로고, 문구)를 따라야 한다. 구글이 정한 규칙이다.

## 확인 질문 (객관식)

**Q1.** OAuth(소셜 로그인)를 쓰면 노트립은 사용자의 구글 비밀번호를?
① 암호화해서 저장한다 ② Supabase에 저장한다 ③ 한 번도 보지 않는다 ④ 처음 한 번만 본다

**Q2.** `signInWithGoogle()`이 로그인 결과(세션)를 바로 돌려주지 않는 이유는?
① 구글이 느려서 ② 브라우저가 구글 사이트로 떠났다가 다시 돌아오는 방식이라서 ③ 비밀번호가 없어서 ④ 에러가 나서

**Q3.** 구글 Client Secret을 `.env.local`의 `VITE_` 변수에 넣으면 안 되는 이유는?
① 이름이 너무 길어서 ② Vercel이 막아서 ③ `VITE_` 변수는 빌드 결과물에 들어가 누구나 볼 수 있어서 ④ 구글이 금지해서

**Q4.** 구글에 "승인된 리디렉션 URI"를 미리 등록하는 이유는?
① 로그인 속도를 높이려고 ② 로그인 결과를 허용된 주소로만 보내서, 해커 사이트로 빼돌리지 못하게 하려고 ③ 구글 광고를 위해 ④ 사용자 이메일을 바꾸려고

**Q5.** 구글 로그인을 추가하면서 AuthProvider(로그인 상태 관리)를 고치지 않아도 된 이유는?
① 구글 로그인은 상태가 없어서 ② 로그인 방식이 달라도 결과는 같은 모양의 세션이라서 ③ AuthProvider가 구글 전용이라서 ④ 아직 테스트를 안 해서

## 추가 (2026-11-23): 카카오 로그인

### 코드: 함수 두 개 → 하나로
구글만 있을 땐 `signInWithGoogle()`이었다. 카카오를 추가하려니 **provider 값만 다른 똑같은 함수**가 하나 더 생기게 됐다. 그래서 `signInWithSocial(provider, redirectPath)` 하나로 합쳤다.
```ts
export type SocialProvider = 'google' | 'kakao'
```
- **유니언 타입**: `'googel'`처럼 오타를 내면 TypeScript가 바로 잡아 준다.
- **"같은 코드가 두 번 나오면 그때 묶는다"**: 처음부터 "나중에 여러 개 생기겠지" 하고 일반화하면, 실제로는 다르게 생긴 요구가 왔을 때 오히려 고치기 어렵다. 실제로 반복이 생겼을 때 묶는 게 안전하다. (면접에서 "리팩터링 경험" 사례로 쓸 수 있다)

### 카카오만의 특징: 이메일을 안 줄 수도 있다
- 카카오 계정은 **전화번호만으로도** 만들 수 있어서 이메일이 없는 사용자가 있다.
- 카카오는 이메일(`account_email`)을 받으려면 **비즈 앱**으로 전환해야 한다. 개인 개발자도 전환할 수 있다.
- 그래서 메뉴에 이메일 대신 이름을 보여주는 **대체 표시**를 넣었다: `이메일 → 공급자가 준 이름 → '나'`.
- 우리 앱은 사용자를 이메일이 아니라 Supabase가 만든 **사용자 id**로 구분한다. 그래서 이메일이 없어도 앱은 동작한다. 2단계에서 여행 테이블도 `user_id`로 연결한다.

**Q6.** `signInWithGoogle`을 `signInWithSocial(provider)`로 합친 이유는?
① 구글이 함수 이름을 바꾸라고 해서 ② provider 값만 다른 같은 코드가 두 번 생겨서 ③ 함수가 많으면 앱이 느려져서 ④ 카카오는 다른 방식이라서

**Q7.** `type SocialProvider = 'google' | 'kakao'`로 정해 두면 좋은 점은?
① 앱 용량이 줄어든다 ② 'googel' 같은 오타를 TypeScript가 잡아 준다 ③ 로그인이 빨라진다 ④ 카카오 설정이 필요 없어진다

**Q8.** 카카오 로그인 사용자의 이메일이 없을 수 있는데도 앱이 동작하는 이유는?
① 카카오가 가짜 이메일을 만들어 줘서 ② 사용자를 이메일이 아니라 Supabase의 사용자 id로 구분해서 ③ 이메일 없으면 로그인이 안 돼서 ④ 이메일을 Vercel에 저장해서

### 보충 문제 (객관식, 오답도 그럴듯하게)

**S1.** `getDisplayName`에서 `user.email ?? ...`을 `user.email || ...`로 바꾼 이유는?
① `??`는 최신 문법이라 일부 휴대폰 브라우저에서 동작하지 않아서
② 이메일이 없으면 Supabase가 빈 문자열("")을 주는데, `??`는 null/undefined일 때만 다음 값으로 넘어가서
③ `||`는 왼쪽부터 차례로 보지만 `??`는 오른쪽부터 봐서
④ TypeScript에서 `??`는 string 타입에 쓸 수 없어서

**S2.** 구글 하나만 있을 때 처음부터 `signInWithSocial(provider)`로 만들지 않은 이유는?
① 공급자가 하나일 때는 유니언 타입을 만들 수 없어서
② 공급자가 하나뿐일 땐 무엇이 달라질지 몰라서, 미리 묶으면 실제로 온 요구와 다른 모양이 될 수 있어서
③ 함수의 인자가 늘어나면 번들 크기가 커져서
④ 그때는 Supabase가 provider를 인자로 받는 기능을 지원하지 않아서

**S3.** 2단계 여행 테이블에서 사용자를 이메일이 아니라 `user_id`로 연결하는 이유로 가장 알맞은 것은?
① 이메일은 개인정보라서 데이터베이스에 저장하는 것 자체가 금지되어서
② 이메일은 없을 수도 있고 나중에 바뀔 수도 있지만, `user_id`는 Supabase가 만들고 바뀌지 않아서
③ `user_id`가 이메일보다 짧아서 검색이 빨라서
④ RLS 정책은 이메일 칸에는 걸 수 없어서

### 채점 (Claude)
S1 ② ✅ · S2 ② ✅ · S3 ② ✅ → **3문제 모두 정답.**

오답이 왜 그럴듯한데 틀렸는지:
- S1
  - ①: `??`는 2020년부터 주요 브라우저가 모두 지원한다. 게다가 Vite가 빌드할 때 필요하면 옛 문법으로 바꿔 준다.
  - ③: 둘 다 **왼쪽부터** 본다. 차이는 "어떤 값을 비었다고 보느냐"뿐이다. `??`는 null/undefined만, `||`는 `""`, `0`, `false`까지 비었다고 본다.
  - ④: `??`는 타입과 상관없이 쓸 수 있다.
- S2
  - ①, ④: 기술적으로는 처음부터 묶을 수 있었다. 묶지 않은 건 **설계 판단**이다.
  - ③: 인자 하나가 늘어도 번들 크기 차이는 무시할 수준이다.
- S3
  - ①: 이메일 저장이 금지된 것은 아니다. 다만 개인정보는 **필요한 만큼만** 두는 게 좋다는 점은 맞다. 이것이 이 오답이 그럴듯한 이유다.
  - ③: 길이 차이가 이유가 아니다. 핵심은 **없을 수 있고 바뀔 수 있다**는 점이다.
  - ④: RLS 정책은 어떤 칸에도 걸 수 있다. 다만 우리는 `auth.uid() = user_id`처럼 id로 건다.
