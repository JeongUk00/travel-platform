>
> 피그마 디자인을 처음으로 코드로 옮긴 작업이다. (UI/UX > 회원가입, 2026-11-25)

## 1. 디자인 토큰: 색과 글꼴에 이름 붙이기

**① 무엇인가**
`#1a2b5f` 같은 값에 `brand-900`처럼 **이름을 붙여 한 곳에 모아 둔 것**이다. Tailwind v4에서는 CSS의 `@theme`에 적는다.
```css
@theme {
  --color-brand-900: #1a2b5f;   /* → bg-brand-900, text-brand-900 … */
  --font-logo: 'Nunito', sans-serif;   /* → font-logo */
}
```

**② 없으면?**: 화면마다 `bg-[#1a2b5f]`처럼 값을 직접 쓰게 된다. 여자친구가 브랜드 색을 조금 바꾸면 모든 화면을 찾아 고쳐야 하고, 하나쯤 빠뜨린다.

**③ 우리 프로젝트에서**: `src/index.css`. 피그마 "브랜드컬러" 프레임의 세 색(1A2B5F, 2C4388, C3C3C3)과 글꼴 두 개.

## 2. 글꼴 셀프 호스팅

**① 무엇인가**
글꼴 파일을 남의 서버(구글 폰트, CDN)에서 받지 않고, npm 패키지로 설치해 **우리 사이트에서 같이 내보내는 것**이다.
- 본문: **Pretendard** (`pretendard` 패키지). 한글 글꼴은 글자가 많아 파일이 수 MB다. 그래서 **dynamic subset** 방식을 쓴다. 파일을 92조각으로 나눠 두고, 화면에 나온 글자가 든 조각만 받는다.
- 로고 글자: **Nunito Black** (`@fontsource/nunito`). 로고에만 쓰므로 영문 900 굵기 하나만 받는다.

**② 없으면(CDN을 쓰면)?**: 그 서버가 느리거나 막히면 글꼴이 늦게 뜬다. 사용자 접속 정보도 그 서버로 간다.

**③ 우리 프로젝트에서**: `src/main.tsx`의 import 두 줄. `index.css`의 `--font-sans`에는 Pretendard를 못 받았을 때 쓸 기기 글꼴을 뒤에 적어 두었다.

> 한계: 지금 Service Worker는 글꼴 파일(`.woff2`)을 미리 저장하지 않는다(`globPatterns`에 없음). 그래서 처음부터 오프라인이면 기기 글꼴로 보인다. 오프라인 기능을 다룰 때 다시 본다.

## 3. 로딩 화면: "최소 시간"과 "할 일" 둘 다 기다리기

**① 무엇인가**
`SplashGate`는 앱 전체(라우터)를 감싸는 문이다. 두 조건이 **모두** 끝나야 실제 화면을 그린다.
1. 로그인 상태 확인이 끝났다 (`loading === false`)
2. 0.8초가 지났다 (`SPLASH_MIN_MS`)

| 상황 | 로딩 화면이 보이는 시간 |
|---|---|
| 확인이 0.1초 만에 끝남 | 0.8초 (번쩍하고 사라지지 않게) |
| 느린 인터넷이라 확인에 3초 걸림 | 3초 (빈 화면이나 잘못된 화면 대신) |

**② 없으면?**
- 최소 시간이 없으면: 로고가 0.1초 번쩍하고 사라져서 화면이 깜빡이는 것처럼 보인다.
- 1~2초를 고정으로 붙잡으면: 앱을 열 때마다 기다려야 해서 자주 쓰는 사람일수록 답답하다. (처음 디자인 의도는 1~2초였고, 0.5~1초로 함께 정했다)

**③ 우리 프로젝트에서**
- `src/app/SplashGate.tsx`: **언제** 보이나. `main.tsx`에서 라우터 바깥을 감싼다. 어느 주소로 들어오든 한 번 나와야 해서 라우터 바깥이다.
- `src/features/onboarding/components/SplashScreen.tsx`: **어떻게** 생겼나.
- 덤: 확인이 끝난 뒤에 라우터를 그리므로, `RequireAuth`의 "확인 중…" 문구가 더 이상 보이지 않는다.
- `vite.config.ts`의 `background_color`도 남색(#2c4388)으로 바꿨다. 안드로이드는 홈 화면 앱을 켤 때 이 색으로 자체 시작 화면을 먼저 그린다. 흰색이면 "흰 화면 → 남색 로딩 화면"으로 번쩍인다.

## 4. 소개 화면: "처음 한 번"을 기억하는 법

**① 무엇인가**
소개 화면(`/welcome`)을 봤는지를 **localStorage**에 `note-trip:intro-seen:v1 = true`로 남긴다.

| 저장 위치 | 언제 사라지나 | 이번에 맞나? |
|---|---|---|
| React state | 새로고침하면 | ❌ |
| sessionStorage | 탭을 닫으면 | ❌ "처음 한 번"이 안 됨 |
| **localStorage** | 사용자가 지우기 전까지 | ✅ |
| Supabase DB | 계속 | ❌ 로그인 **전**이라 누군지 모름 |

**② 없으면?**: 앱을 열 때마다 소개 화면이 나온다.

**③ 우리 프로젝트에서**
- `src/features/onboarding/introSeen.ts`: 읽기/쓰기 함수. **try/catch**로 감쌌다. 사파리 개인정보 보호 모드 등에서는 localStorage에 접근만 해도 오류가 나는데, "있으면 좋은" 기능 때문에 앱이 멈추면 안 되기 때문이다.
- 키에 `v1`을 붙였다. 소개 화면을 새로 만들어 모두에게 다시 보여 주고 싶으면 `v2`로 바꾸면 된다.
- "봤다" 표시는 화면이 열릴 때가 아니라 **"여행 시작하기"를 눌렀을 때** 남긴다.
- 누구를 어디로 보낼지는 `RequireAuth` 한 곳이 정한다: 로그인 안 됨 + 안 봄 → `/welcome`, 로그인 안 됨 + 봄 → `/login`.
- 원래 가려던 주소(`state.from`)는 소개 → 로그인까지 그대로 들고 간다. (카톡으로 받은 여행 링크 → 소개 → 로그인 → 그 여행)

## 5. 피그마 값을 그대로 옮기지 않은 곳

피그마는 **393×852 한 크기의 그림**이고, 실제 폰은 크기가 제각각이다.
- 위치를 px 대신 **화면 높이 비율(dvh)**로 옮겼다. 글 묶음 위 178px → `21dvh`, 버튼 아래 163px → `19dvh`.
- 처음엔 비율만 옮겼더니 **360×640 화면에서 글과 버튼이 붙었다.** 그래서 문단 간격을 `min(67px, 7.9dvh)`로 바꾸고, 버튼 위에 최소 28px(`mb-7`)을 두었다. 디자인 크기(393×852)에서는 피그마와 똑같다.
- 피그마의 휴대폰 틀(회색 테두리, 9:41 상태 표시줄)은 만들지 않는다. 진짜 폰이 직접 보여 준다.

## 확인 질문 (객관식)

**Q1.** 로딩 화면을 "1.5초 고정"이 아니라 "확인이 끝날 때까지, 단 최소 0.8초"로 만든 이유로 가장 알맞은 것은?
① 0.8초 동안 Supabase가 로그인 정보를 미리 받아 두어 이후 화면이 빨라지기 때문에
② 브라우저가 0.8초 안에 그려지지 않은 화면은 자동으로 숨기기 때문에
③ 1.5초로 고정하면 안드로이드 시작 화면과 겹쳐 두 번 보이기 때문에
④ 고정 시간은 자주 쓰는 사람을 기다리게 하고, 최소 시간이 없으면 확인이 빠를 때 로고가 번쩍이고 사라지기 때문에

**Q2.** "소개 화면을 봤다"는 기록을 Supabase DB가 아니라 localStorage에 둔 이유는?
① 소개 화면은 로그인 **전**에 보여서, 아직 누구의 기록인지 정할 수 없기 때문에
② DB에 쓰면 RLS 때문에 소개 화면 기록이 다른 사용자에게 보이기 때문에
③ localStorage가 DB보다 안전해서 사용자가 값을 바꿀 수 없기 때문에
④ Supabase 무료 요금제는 사용자마다 저장할 수 있는 칸 수가 정해져 있기 때문에

**Q3.** `hasSeenIntro()`를 try/catch로 감싸고, 실패하면 `false`를 돌려주게 한 이유는?
① localStorage는 비동기라서 try/catch가 없으면 값을 기다리지 않기 때문에
② 일부 환경에서는 localStorage 접근 자체가 오류를 내는데, 그것 때문에 앱이 멈추면 안 되고 소개 화면을 한 번 더 보여 주는 정도는 괜찮기 때문에
③ false를 돌려줘야 RequireAuth가 로그인 화면으로 보내기 때문에
④ TypeScript는 localStorage를 쓸 때 try/catch를 반드시 요구하기 때문에

**Q4.** `SplashGate`를 각 화면(라우트) 안이 아니라 `main.tsx`에서 라우터 바깥에 둔 이유는?
① 라우터 안에서는 setTimeout을 쓸 수 없기 때문에
② 라우터 바깥에 두면 번들 크기가 줄어들기 때문에
③ 어느 주소로 들어오든 앱을 켤 때 한 번 보여야 하고, 확인이 끝난 뒤 라우터를 그리면 안쪽 화면들은 "확인 중"을 신경 쓰지 않아도 되기 때문에
④ useAuth는 라우터 바깥에서만 쓸 수 있기 때문에

**Q5.** 피그마의 "위에서 178px"을 `pt-[178px]`이 아니라 `pt-[21dvh]`로 옮긴 이유는?
① dvh가 px보다 브라우저에서 더 빨리 계산되기 때문에
② Tailwind는 100px이 넘는 값을 px로 쓸 수 없기 때문에
③ px로 쓰면 다크 모드에서 위치가 달라지기 때문에
④ 피그마는 한 크기(852px 높이)의 그림이라, 폰 높이가 달라도 비슷한 비율로 보이게 하려고

### 채점 (Claude)
Q1 ④ ✅ · Q2 ① ✅ · Q3 ③ ❌ (정답 ②) · Q4 ② ❌ (정답 ③) · Q5 ④ ✅ → **5문제 중 3문제 정답.**

**Q3: 고른 답 ③ "false를 돌려줘야 RequireAuth가 로그인 화면으로 보내기 때문에"**
- 방향이 반대다. `hasSeenIntro()`가 false면 "아직 안 봤다"는 뜻이라 **소개 화면(/welcome)**으로 보낸다. 로그인 화면(/login)은 true일 때다.
  ```ts
  const destination = hasSeenIntro() ? '/login' : '/welcome'
  ```
- try/catch의 핵심은 **"실패해도 앱이 멈추지 않게"**다. 사파리 개인정보 보호 모드 등에서는 localStorage를 읽기만 해도 오류(예외)가 난다. 잡지 않으면 그 오류가 RequireAuth까지 올라가서 **화면 전체가 하얗게 멈춘다.**
- 실패했을 때 false를 고른 이유: 그러면 최악의 경우가 "소개 화면을 한 번 더 본다"로 끝난다. 반대로 true를 돌려주면 처음 온 사람이 소개를 못 보고 지나간다. **실패했을 때 덜 나쁜 쪽**을 고른 것이다.

**Q4: 고른 답 ② "라우터 바깥에 두면 번들 크기가 줄어들기 때문에"**
- 코드를 어디에 놓든 **같은 코드는 같은 크기로** 번들에 들어간다. 위치는 크기가 아니라 **언제, 어디서 실행되느냐**를 바꾼다.
- 진짜 이유는 두 가지다.
  1. **어느 주소로 들어오든** 앱을 켤 때 한 번 나와야 한다. 라우트마다 넣으면 `/trips/busan` 같은 딥 링크 경로를 빠뜨리기 쉽다.
  2. 확인이 끝난 **뒤에** 라우터를 그리므로, 안쪽 화면(RequireAuth, LoginPage)은 "아직 확인 중"인 상태를 만날 일이 없다. (그래서 RequireAuth의 "확인 중…" 문구가 이제 안 보인다)

### 보충 문제 (Q3, Q4 다시 확인)

**S1.** 사파리 개인정보 보호 모드에서 `localStorage.getItem()`이 오류를 냈다. `hasSeenIntro()`에 try/catch가 **없었다면** 어떻게 될까?
① 브라우저가 자동으로 sessionStorage에서 대신 읽어 와서 아무 일도 없다
② `hasSeenIntro()`가 undefined를 돌려줘서 로그인 화면으로 간다
③ 오류가 RequireAuth까지 올라가 화면을 그리지 못하고, 사용자는 빈 화면을 보게 된다
④ 소개 화면이 한 번 더 보인다

**S2.** 다음 중 `SplashGate`를 라우터 **바깥**에 둔 덕분에 생긴 일로 맞는 것은?
① 로그인 상태 확인이 끝난 뒤에 라우터가 그려져서, RequireAuth의 "로그인 상태를 확인하는 중…" 문구가 더 이상 보이지 않는다
② 라우터 바깥의 코드는 Service Worker가 따로 저장해서 오프라인에서도 로딩 화면이 더 빨리 뜬다
③ 화면을 이동할 때마다(예: 여행 목록 → 여행 상세) 로딩 화면이 0.8초씩 다시 나온다
④ SplashScreen 코드가 첫 화면에만 들어가고 나머지 화면의 번들에서는 빠진다

### 채점 (Claude)
S1 ③ ✅ · S2 ④ ❌ (정답 ①)

**S1 정답.** try/catch가 없으면 오류가 위로 올라가 화면이 멈춘다는 점을 정확히 잡았다. (Q3 보완 완료)

**S2: 고른 답 ④ "SplashScreen 코드가 첫 화면에만 들어가고 나머지 화면의 번들에서는 빠진다"**
Q4(②)와 같은 오해가 한 번 더 나왔다. "컴포넌트를 어디에 놓느냐"와 "코드가 어느 파일에 들어가느냐"는 **서로 다른 이야기**다.

| | 무엇을 정하나 | 우리 프로젝트 |
|---|---|---|
| **컴포넌트 트리**의 위치 (라우터 안/밖) | **언제, 무엇을 그릴지** (실행 순서) | SplashGate가 RouterProvider를 감쌈 |
| **번들 파일** 나누기 | 브라우저가 **어떤 JS 파일을 언제 받을지** | 지금은 `index-xxxx.js` **한 파일**에 전부 들어 있음 |

- `npm run build` 결과를 보면 JS 파일은 `dist/assets/index-CGSk4Bfs.js` **하나**뿐이다. SplashScreen, IntroPage, LoginPage, TripListPage가 모두 이 파일 안에 있다.
- 파일을 나누려면 `import()`(동적 import)나 `React.lazy`를 따로 써야 한다(**코드 분할**). 컴포넌트를 라우터 안이나 밖으로 옮기는 것만으로는 파일이 나뉘지 않는다.
- 그래서 S2의 ②, ④처럼 "위치 때문에 파일, 저장, 크기가 달라진다"는 보기는 모두 틀리다. 라우터 바깥에 둔 효과는 **실행 순서**뿐이다. 확인이 끝난 뒤에 라우터를 그리기 때문에 "확인 중…" 문구가 사라졌다(①).
- ③은 반대다. SplashGate는 앱이 켜질 때 한 번 마운트되고, 화면을 이동해도 다시 마운트되지 않는다. 그래서 로딩 화면은 다시 나오지 않는다.

### 보충 문제 2

**S3.** 빌드 경고("JS 파일이 500KB를 넘는다")를 줄이려고 할 때, 실제로 JS 파일을 나누는 방법은?
① SplashGate처럼 컴포넌트를 라우터 바깥으로 옮긴다
② 컴포넌트를 `features/` 아래 다른 폴더로 옮긴다
③ 화면마다 `export function` 대신 `export default`로 바꾼다
④ `React.lazy(() => import('./TripDetailPage'))`처럼 동적 import로 불러온다

**S4.** 다음 중 맞는 설명은?
① 컴포넌트를 라우터 바깥에 두면 그 컴포넌트는 별도 파일로 빌드된다
② 컴포넌트 트리의 위치는 실행 순서를 바꾸고, 번들 파일 구성은 import 방식(정적/동적)이 정한다
③ 폴더 구조가 곧 번들 파일 구조라서, 폴더마다 JS 파일이 하나씩 생긴다
④ 지금 노트립의 JS 파일은 화면 개수만큼 나뉘어 있다
