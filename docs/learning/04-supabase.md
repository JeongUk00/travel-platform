# 학습 04. Supabase와 환경 변수

> 순서: ① 무엇인가 → ② 없으면 무슨 문제 → ③ 우리 프로젝트의 어디에 있나 → 확인 질문

---

## 1. 프론트엔드와 백엔드

**기준은 "코드가 어디서 실행되느냐"**다.

| | 프론트엔드 | 백엔드 |
|---|---|---|
| 실행 위치 | 사용자의 폰이나 브라우저 | 서버 (인터넷 너머의 컴퓨터) |
| 하는 일 | 화면 보여주기, 버튼 반응, 화면 이동 | 데이터 저장, 로그인 확인, 권한 검사 |
| 비유 | 식당의 홀 | 식당의 주방과 창고 |
| 우리 프로젝트 | `src/`의 React 코드 | **Supabase** |

프론트엔드 안에도 두 층이 있다. **화면의 "모양"**(색, 배치)은 디자인이 필요하고, **화면의 "로직"**(화면 이동, 로그인 흐름, 데이터 주고받기)은 디자인 없이도 만들 수 있다.

---

## 2. Supabase: 빌려 쓰는 백엔드

**① 무엇인가**
DB(PostgreSQL), 로그인, 파일 저장, 실시간 동기화를 **완성된 형태로 빌려주는 서비스**. 이런 서비스를 **BaaS(Backend as a Service)**라고 한다.

**② 없으면?**
Java(Spring)나 Node.js로 서버 코드를 직접 짜고, 서버 컴퓨터를 빌려 24시간 켜 두고, DB를 설치하고, 로그인과 보안을 직접 구현해야 한다. 비용도 들고, 1인 개발로는 범위가 너무 크다.

**우리가 직접 하는 것**: DB 테이블 설계(SQL), 권한 규칙(RLS) 작성, 비밀 키가 필요한 일부 기능(Edge Function).

**버린 대안**: Firebase. 설정은 쉽지만 NoSQL이라, 정산처럼 "여행 ↔ 사람 ↔ 지출"이 얽힌 데이터를 다루기 불리하다. Supabase는 진짜 SQL을 쓰므로 DB 공부도 된다. (설계 문서 2절)

**③ 우리 프로젝트에서**: `src/lib/supabase.ts`

```ts
export const supabase = createClient(supabaseUrl, supabaseKey)
```
- `@supabase/supabase-js`: Supabase와 대화하는 **클라이언트 라이브러리**. 이 객체로 `supabase.auth.signIn...`(로그인), `supabase.from('trips').select()`(데이터 읽기) 같은 일을 한다.
- **이 파일 하나에서만 만든다.** 여러 곳에서 만들면 로그인 상태를 기억하는 객체가 여러 개 생겨 상태가 어긋날 수 있다. 앱 전체에 하나만 두는 방식을 **싱글톤**이라고 한다.

## 3. 환경 변수: 코드 밖에 두는 설정값

**① 무엇인가**
코드에 직접 쓰지 않고 **실행 환경마다 따로 넣어 주는 값**. Supabase 주소와 키가 대표적이다.

```ts
// ❌ 코드에 직접
const url = 'https://abcd.supabase.co'
// ✅ 환경 변수에서
const url = import.meta.env.VITE_SUPABASE_URL
```

**② 없으면?**
- 개발용과 실제 서비스용 DB를 나누려면 **코드를 고쳐야** 한다.
- 키가 **Git 기록에 영원히 남는다.** 지워도 예전 커밋에 남아 있다.

**③ 우리 프로젝트에서**

| 파일 | Git에 올라가나 | 역할 |
|---|---|---|
| `.env.example` | ✅ 올라감 | **어떤 변수가 필요한지** 알려 주는 빈 양식. 새 기기나 새 사람이 보고 따라 만든다 |
| `.env.local` | ❌ 안 올라감 (`.gitignore`의 `*.local`) | **실제 값**이 들어 있는 파일. 내 컴퓨터(USB)에만 있다 |
| Vercel 설정 화면 | – | 배포 사이트용 실제 값. Vercel은 `.env.local`을 볼 수 없으므로 따로 넣는다 |
| `src/vite-env.d.ts` | ✅ | 환경 변수 **이름과 타입**을 TypeScript에 알려 준다. 이름을 잘못 쓰면 오류로 잡힌다 |

**Vite의 `VITE_` 규칙**
Vite는 이름이 `VITE_`로 시작하는 변수만 앱 코드에 넣어 준다. 그리고 넣어 준 값은 **빌드 결과물(JS 파일)에 그대로 박힌다.** 즉 `VITE_` 변수는 **누구나 볼 수 있다**고 생각해야 한다. 비밀 값이 실수로 새지 않도록 이름으로 구분하는 장치다.

**fail fast**: `supabase.ts`는 값이 없으면 시작하자마자 오류를 낸다. 값이 빈 채로 진행하면 엉뚱한 곳에서 알 수 없는 오류가 나서 원인을 찾기 어렵기 때문이다.

## 4. 키가 공개돼도 괜찮은가?

Supabase 키는 두 종류다.

| 키 | 어디에 쓰나 | 공개되면? |
|---|---|---|
| **Publishable key** (`sb_publishable_...`) | 브라우저 (우리 앱) | **괜찮다.** 이 키로는 RLS 규칙이 허락한 것만 할 수 있다 |
| **Secret key** (`sb_secret_...`) | 서버에서만 | **큰일.** 모든 규칙을 무시하고 DB 전체를 읽고 지울 수 있다 |

> 예전 이름: anon key = publishable key, service_role key = secret key

**왜 publishable key는 공개돼도 되나? → RLS(Row Level Security) 덕분이다.**
- 프론트엔드 코드는 사용자 폰에서 실행되므로 **사용자가 얼마든지 열어 보고 조작할 수 있다.** 프론트엔드에 숨긴 비밀은 비밀이 아니다.
- 그래서 "누가 무엇을 볼 수 있나"는 **DB가 직접 검사**한다. 예: "이 여행의 멤버만 이 일정을 읽을 수 있다"를 SQL 규칙으로 걸어 둔다.
- 키는 **문을 여는 것**일 뿐이고, 들어가서 무엇을 할 수 있는지는 RLS가 정한다.

⚠️ 반대로 말하면 **RLS를 켜지 않은 테이블은 publishable key만 있으면 누구나 읽고 쓸 수 있다.** 그래서 테이블을 만들 때마다 RLS를 반드시 켠다.

## 5. 배포할 때 주의

`supabase.ts`는 아직 어떤 화면에서도 쓰지 않아서 빌드 결과물에 포함되지 않는다. (안 쓰는 코드는 Vite가 빼 버린다: tree shaking)
**처음으로 화면에서 `supabase`를 쓰는 순간**, Vercel에도 환경 변수를 넣어야 한다. 안 넣으면 배포 사이트가 시작하자마자 위의 fail fast 오류로 멈춘다.

## 내 답 (직접 작성)

1. 화면에 보이는 것과 인터넷 너머. React, Supabase
2. 로그인 상태를 기억하는 객체가 여러 개가 생길 수 있는 문제가 발생할 수 있기 때문이다.
3. .env.example은 양식 같은 것이고, .env.local은 직접 값이 들어가있는 파일. .env.local의 값이 올라가면 다른 사람이 볼 수 있기 때문
4. 빌드 결과물에 그대로 박히기 때문
5. RLS 덕분. 누구나 publishable key만 있으면 누구나 읽고 쓰게 됨.

## 검토 (Claude)

1. **절반 정답.** 예시(React, Supabase)는 맞다. 하지만 기준을 "화면에 보이는 것"으로 잡으면 틀린다. 화면 이동, 로그인 흐름, 데이터 요청처럼 **눈에 안 보여도 폰에서 실행되는 코드는 프론트엔드**다. 기준은 **"코드가 어디서 실행되느냐"**(사용자 기기 vs 서버)이다.
2. **정답.** 이렇게 하나만 두는 방식을 **싱글톤**이라고 부른다는 것까지 기억해 두기.
3. **정답.** 하나 덧붙이면 `.env.example`을 **굳이 올리는 이유**도 말할 수 있어야 한다. 새 기기(데스크탑)나 새 사람이 "어떤 변수가 필요한지" 알 수 있게 하기 위해서다. 값이 비어 있으니 올려도 안전하다.
4. **정답.** 한 단계 더 이어 보면: 빌드 결과물(JS 파일)은 **모든 사용자의 브라우저로 내려받아지므로**, 누구나 개발자 도구로 열어 볼 수 있다.
5. **결과는 맞음, 이유가 짧음.** "RLS 덕분"의 **원리**까지 말해야 한다.
   → 키는 **문을 여는 것**일 뿐이고, 들어와서 무엇을 읽고 쓸 수 있는지는 **DB가 행(row)마다 직접 검사**한다(RLS). 그래서 키가 공개돼도 규칙이 허락한 것만 할 수 있다. 반대로 RLS를 안 켠 테이블은 누구나 읽고 쓸 수 있다.

→ 이번에도 **"무엇"은 맞고 "왜, 어떻게"가 짧은** 패턴이 1번과 5번에서 보인다.
