# 학습 01. 0단계에서 쓴 도구들은 무엇이고 왜 쓰나

> 각 도구마다 **① 무엇인가 → ② 없으면 무슨 문제가 생기나 → ③ 우리 프로젝트의 어디에 있나** 순서로 정리한다.
> 마지막의 "확인 질문"에 답할 수 있어야 다음 단계로 넘어간다.

---

## 0. 출발점: 브라우저는 딱 3가지만 안다

브라우저가 이해하는 것은 결국 이 세 가지뿐이다.

| 언어 | 역할 | 비유 |
|---|---|---|
| **HTML** | 화면에 무엇이 있는지 (제목, 버튼, 글) | 집의 뼈대 |
| **CSS** | 어떻게 보이는지 (색, 크기, 배치) | 인테리어 |
| **JavaScript** | 어떻게 움직이는지 (클릭하면 무슨 일이 일어나는지) | 전기, 수도 |

아래 도구들은 전부 **"이 3가지를 사람이 더 편하고 안전하게 작성하도록"** 돕는 도구다.
최종적으로는 모두 HTML, CSS, JS로 바뀌어 브라우저에 전달된다. `npm run build`를 하면 `dist/` 폴더에 그 결과물이 생긴다.

---

## 1. React: 화면을 "부품"으로 만드는 라이브러리

**① 무엇인가**
화면을 **컴포넌트**라는 부품으로 나눠 만든다. 예를 들어 "일정 카드" 부품을 하나 만들어 두면, 일정이 10개일 때 그 부품을 10번 쓰면 된다.
그리고 **데이터가 바뀌면 화면을 알아서 다시 그린다.**

**② 없으면?**
순수 JavaScript로는 "일정 하나가 추가되면 → 목록에서 그 자리를 찾아 → 새 HTML을 끼워 넣고 → 개수 표시도 고치고…"를 전부 직접 해야 한다. 기능이 많아지면 어디를 고쳐야 할지 놓치기 쉽다.
React에서는 **"데이터가 이렇게 생겼으면 화면은 이렇게 생겼다"만 선언**하면 된다.

**③ 우리 프로젝트에서**
- `src/App.tsx`: 첫 번째 컴포넌트. `function App() { return <main>...</main> }`
- `src/main.tsx`: `index.html`의 `<div id="root">` 안에 App 컴포넌트를 붙이는 시작점

> HTML처럼 생긴 `<main>...</main>` 문법을 **JSX**라고 한다. 브라우저는 이걸 모르기 때문에, 아래의 Vite가 JS로 바꿔 준다.

---

## 2. TypeScript: 타입이 있는 JavaScript

**① 무엇인가**
JavaScript에 **"이 변수에는 어떤 종류의 값이 들어가는가"(타입)**를 적을 수 있게 한 언어다.

```ts
// JavaScript: 실행해 보기 전까지 실수를 모른다
function 나누기(금액, 인원) { return 금액 / 인원 }
나누기("10000", 3)   // 문자열을 넣어도 일단 실행된다

// TypeScript: 코드를 쓰는 순간 빨간 줄이 뜬다
function 나누기(금액: number, 인원: number) { return 금액 / 인원 }
나누기("10000", 3)   // ❌ 오류: string은 number에 넣을 수 없음
```

**② 없으면?**
정산처럼 돈을 다루는 코드에서 숫자 대신 문자열이 들어가는 실수가, **사용자가 쓰다가** 발견된다.
TypeScript를 쓰면 **코드를 쓰는 순간** 발견된다. 버그를 사용자보다 먼저 잡는 것이다.

**③ 우리 프로젝트에서**
- 파일 확장자가 `.ts`, `.tsx`다. (`.tsx` = TypeScript + JSX)
- `tsconfig.json`, `tsconfig.app.json`: TypeScript를 얼마나 엄격하게 검사할지 정하는 설정
- `npm run build`의 앞부분인 `tsc -b`가 타입 검사를 한다. 타입 오류가 있으면 빌드가 멈춘다.
- 브라우저는 TypeScript를 모르므로, 빌드할 때 타입 정보를 지우고 JS로 바꾼다.

## 3. Vite: 개발 서버 + 빌드 도구

**① 무엇인가**
두 가지 일을 한다.
1. **개발 중** (`npm run dev`): 코드를 저장하면 브라우저 화면이 **즉시** 바뀌는 개발 서버를 띄운다. (HMR, Hot Module Replacement)
2. **배포 전** (`npm run build`): TSX, TS, Tailwind를 **브라우저가 아는 HTML, CSS, JS로 변환**하고, 파일을 합치고 압축해서 `dist/`에 만든다.

**② 없으면?**
TSX를 JS로 바꾸고, 파일 수십 개를 합치고, 압축하는 일을 전부 손으로 해야 한다.
예전 도구인 Webpack은 이 일을 하긴 하지만, 프로젝트가 커지면 개발 서버가 켜지는 데만 수십 초씩 걸렸다. Vite는 필요한 파일만 그때그때 변환해서 빠르다.

**③ 우리 프로젝트에서**
- `vite.config.ts`: 어떤 플러그인을 거칠지 설정 (`react()`, `tailwindcss()`)
- `index.html`: Vite가 이 파일을 출발점으로 삼아 `src/main.tsx`를 찾아간다.
- `package.json`의 `scripts`: `dev`, `build`, `preview` 명령이 Vite를 실행한다.

> **"Vite + React + TS 프로젝트를 만들었다"는 것은 사실 명령어 한 줄**(`npm create vite@latest`)이다. Vite가 위 파일들의 기본 틀(템플릿)을 만들어 준다. 직접 해 보는 실습은 맨 아래에 있다.

## 4. 린터(Linter), ESLint, oxlint: 코드 검사기

**① 무엇인가**
**린터**는 코드를 실행하지 않고 읽기만 해서 **버그가 될 만한 패턴이나 나쁜 습관**을 찾아 주는 도구다. 글쓰기로 치면 맞춤법 검사기다.

```tsx
// 린터가 잡아 주는 예: React 훅을 if 안에서 부르면 버그가 생긴다
if (로그인했다면) {
  const [x, setX] = useState(0)   // ⚠️ react/rules-of-hooks 규칙 위반
}
```

TypeScript가 **"값의 종류가 맞는가"**를 검사한다면, 린터는 **"이렇게 쓰면 위험하거나 읽기 어렵다"**를 검사한다. 서로 역할이 다르다.

- **ESLint**: 가장 오래되고 널리 쓰이는 JavaScript 린터. 규칙과 플러그인이 아주 많다. JavaScript로 만들어져 있다.
- **oxlint**: Rust로 만든 새 린터. ESLint의 주요 규칙을 지원하면서 **50~100배 빠르고** 설정이 단순하다.

**② 없으면?**
위 같은 실수를 사람이 눈으로 찾아야 한다. 팀 프로젝트에서는 사람마다 코드 스타일이 달라져 읽기 어려워진다.

**③ 우리 프로젝트에서**
- `.oxlintrc.json`: 어떤 규칙을 켤지 설정. `react/rules-of-hooks`를 `error`로 켜 두었다.
- `npm run lint`로 실행한다.

**왜 ESLint가 아니라 oxlint?**
이 프로젝트는 규칙을 복잡하게 커스터마이징할 일이 없고 빠르고 단순한 게 낫다고 판단했다.
다만 **실무에서는 아직 ESLint가 더 흔하다.** 면접에서는 "ESLint가 표준이라는 것을 알고, 개인 프로젝트에서는 속도와 단순함 때문에 oxlint를 골랐다"고 설명하면 된다.

## 5. Tailwind CSS: 클래스 이름으로 스타일을 입히는 CSS 도구

**① 무엇인가**
CSS를 따로 쓰는 대신, **미리 정해진 짧은 클래스 이름을 HTML에 붙여서** 스타일을 입힌다.

```tsx
// 일반 CSS: 파일 두 개를 오가며 작성
// App.css →  .title { font-size: 1.5rem; font-weight: 700; }
<h1 className="title">여행 플랫폼</h1>

// Tailwind: 그 자리에서 바로
<h1 className="text-2xl font-bold">여행 플랫폼</h1>
```

**② 없으면?**
- 클래스 이름을 매번 지어야 한다. (`.title`? `.header-title`? `.main-title`?)
- CSS 파일과 컴포넌트 파일을 오가야 한다.
- 안 쓰는 CSS가 계속 쌓인다. 지워도 되는지 확신하기 어렵기 때문이다.

Tailwind는 **코드에서 실제로 쓴 클래스만 골라** CSS 파일을 만든다. 우리 빌드 결과물이 6.8KB인 이유다.

**단점도 있다**: 클래스가 길어지면 HTML이 지저분해 보인다. 그래서 반복되는 부분은 컴포넌트로 묶는다.

**③ 우리 프로젝트에서**
- `src/index.css`의 `@import 'tailwindcss';`
- `vite.config.ts`의 `tailwindcss()` 플러그인
- `src/App.tsx`의 `className="..."`

## 6. 전체 흐름 한 장 요약

```
내가 쓰는 코드                    도구                        브라우저가 받는 것
─────────────────               ──────────                   ─────────────────
App.tsx (React+TS+JSX)  ──┐
                          ├──►  Vite ──► dist/assets/*.js    (JavaScript)
main.tsx                ──┘     ├ TS → JS 변환
                                ├ JSX → JS 변환
index.css + className   ──────► ├ Tailwind → CSS ──► dist/assets/*.css (CSS)
index.html              ──────► └ 합치기, 압축 ──► dist/index.html  (HTML)

                     oxlint: 코드를 읽기만 하고 위험한 패턴을 경고 (결과물에는 영향 없음)
                     tsc:    타입이 맞는지 검사 (틀리면 빌드 중단)
```

## 내 답 (직접 작성)

1. 브라우저는 TSX파일을 직접 읽을 수 없다. 빌드 할 때 타입 정보를 지우고 JS로 바꾼다.
2. TypeScript는 값의 종류가 맞는가? 린터는 이렇게 쓰면 위험하거나 읽기 어렵다를 검사.
3. npm run dev는 개발중 코드를 저장하면 화면이 즉시 바뀌는 개발 서버, npm run build는 배포전 TSX, TS, Tailwind를 브라우저가 아는 HTML , CSS, JS로 변환
4. 코드에서 실제로 쓴 클래스만 골라서 CSS 파일을 만들기 때문
5. 50~100배 더 빠르고 설정이 단순.. 실무에서는 ESLint가 더 흔함.
## 검토 (Claude)

전체적으로 핵심은 다 맞았다. 빠진 부분만 짚는다.

1. **절반 정답.** "누가"가 빠졌다. → **Vite**가 바꿔 준다. 그리고 바뀌는 건 타입만이 아니다. **JSX(`<main>...</main>`)도 JS 함수 호출로 바뀐다.** 또 빌드 때만이 아니라 `npm run dev` 중에도 Vite가 그때그때 변환해서 브라우저에 준다.
2. **정답.** 덧붙이면 둘 다 "코드를 실행하지 않고" 검사한다는 공통점이 있다. 그래서 둘 다 **정적 분석**이라고 부른다.
3. **정답.** 덧붙이면 `build`는 변환 전에 `tsc -b`로 **타입 검사를 먼저** 하고, 오류가 있으면 멈춘다. 결과물은 `dist/` 폴더에 생긴다.
4. **정답.**
5. **절반 정답.** "빠르고 단순하다"는 oxlint의 장점이지, **이 프로젝트에서 고른 이유**까지는 아니다. 이유는 "1인 프로젝트라 ESLint의 복잡한 커스텀 규칙과 플러그인이 필요 없었기 때문"이다. 면접에서는 "장점"보다 **"내 상황에서 왜 그게 맞았나"**를 말해야 설득력이 있다.
